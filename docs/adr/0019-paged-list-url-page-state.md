# Paged-list primitive: the URL holds the page, each list keeps its fetch

Ticket #42 (found in the two-axis review of #40): the categories panel fetched the list once with the API's defaults, so past 100 rows the list silently truncated. The fix is one shared frontend paged-list module — `usePageParam` (`hooks/`, the one-home rule's home for generic hooks) plus `<PagedList>` (`components/shared/`, the home for app-wide pieces) — with the categories panel as its first consumer and #6/#7/#8 (products, customers, suppliers) as the intended ones.

The primitive owns exactly: the page position in the URL's `?page=` param (0-based — the same number the API takes, so the URL param *is* the API param and there is no conversion layer to get wrong); clamping a missing/garbage value to page 0; the prev/next controls with their bounds; the "x–y of total" summary; and the loading/empty/error states around the rows. The summary reads the *returned* envelope (page, size, total, totalPages) — the server's answer, never the client's request. Each list keeps: its endpoint, its query key (which now includes the page number; React Query's prefix invalidation still clears every cached page), its rows as children, and its mutations. Page size stays the API default (100, its max) — no size picker until a list actually asks for one; that is the honesty-for-one-consumer line.

URL sync goes through `router.replace(..., { scroll: false })`, matching the filter policy already recorded in frontend-architecture §Data fetching: a page is shareable and survives a reload, and clicking through pages does not litter the history stack (back leaves the list, not the previous page — filters share the same decision). Rejected: a *fetching* primitive (endpoints, query keys and future filters vary per list — it would trade per-list code for per-list configuration without hiding anything); plain local state without the URL (not shareable, contradicts the documented filter policy); `push` per page (history spam). Revisit when #6/#7/#8 land: search/filter params extend the same URL-param pattern the hook already preserves when it rewrites `page`; if a list ever needs jump-to-page or multi-select filters, the primitive grows then — not before, and not speculatively now.

Amended after the two-axis review of #42 (all before #6): the primitive also owns the **rescue state** for a URL past the last page — the backend answers the truth rather than clamping, so zero items on a list that *has* rows means the URL outlived the list; the component then renders a 1-based "Page N of M" and a single "Go to last page" control (a button, not a link: the component is handed a callback and knows no URLs, and prev/next would only step through more dead pages). A genuinely empty list (`total === 0`) keeps the plain message and no controls. The envelope type lives in `types/` (architecture.md §7's DTO-mirror home), and the valid-page rule is one exported pure function, `toPage` (in its own leaf module, `hooks/to-page.ts`, since the seed must import it into the RSC graph). Resolved before #6: the first page is server-seeded as dehydrated state into a `HydrationBoundary` per ADR 0020 (issue #44) — each list keeps its fetch exactly as described here.
