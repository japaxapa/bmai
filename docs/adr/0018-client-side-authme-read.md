# Auth provider reads `/auth/me` from the browser, not the server

Slice 3 of #4 was specced as "server-read cookie → `GET /api/auth/me`": a server component reading `cookies()` and fetching the user before first paint. The shipped implementation is a client-side read instead — the `"use client"` auth provider calls `fetch("/auth/me", { credentials: "include" })` and the browser attaches the httpOnly cookie (CORS from #3 already allows exactly this from `http://localhost:3000`). Accepted, deliberately, on 2026-10-09: the client read is simpler (no server-to-API hop, no server-side "not logged in" path to model), the cookie is httpOnly either way, and nothing needed the user during SSR yet. The consequence: the first HTML has no user info — the header shows a loading state until the JS fetch lands. Revisit if first-paint personalization or no-JS rendering ever matters; that is the point a real server-read becomes worth its moving parts.
